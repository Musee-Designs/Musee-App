# Musee — Firestore Database Schema

## 1. Overview

Cloud Firestore will store application data, including user profiles, music posts, following relationships, likes, and saved songs.

Firebase Authentication will manage user authentication. Spotify Web API will provide music metadata such as song titles, artists, album artwork, and Spotify links.

This document defines the proposed Firestore data model, expected queries, security requirements, and database usage considerations.

## 2. Database Structure

The initial Firestore database will use two top-level collections: `users` and `posts`.

```text
firestore/
├── users/
│   └── {userId}/
│       ├── followers/          # Future/derived relationship
│       ├── following/
│       │   └── {followedUserId}
│       └── savedSongs/
│           └── {spotifyTrackId}
│
└── posts/
    └── {postId}/
        └── likes/
            └── {userId}
```

All user IDs will correspond to Firebase Authentication UIDs.

## 3. Collections and Data Models

### 3.1 Users Collection

**Path:** `users/{userId}`

Stores public-facing profile information for each registered user.

| Field | Type | Required | Description |
|---|---|---|---|
| uid | string | Yes | Firebase Authentication UID |
| username | string | Yes | Username displayed in the app |
| displayName | string | Yes | User's display name |
| bio | string | Yes | Profile biography |
| photoURL | string or null | Yes | Profile image URL |
| createdAt | Timestamp | Yes | Account creation timestamp |
| updatedAt | Timestamp | Yes | Last profile update timestamp |

Example:

```json
{
  "uid": "user_123",
  "username": "musiclover",
  "displayName": "Music Lover",
  "bio": "Always looking for new music!",
  "photoURL": null,
  "createdAt": "<Firestore Timestamp>",
  "updatedAt": "<Firestore Timestamp>"
}
```

**Notes:**
- The document ID must match the authenticated user's UID.
- Passwords and authentication credentials are managed by Firebase Authentication, not Firestore.
- Usernames are not guaranteed to be unique in this initial design.
- Profile data is readable by authenticated Musee users.
- Only the profile owner can create or update their profile.

### 3.2 Posts Collection

**Path:** `posts/{postId}`

Stores songs shared by users, along with optional captions and moods.

| Field | Type | Required | Description |
|---|---|---|---|
| id | string | Yes | Firestore post document ID |
| authorId | string | Yes | UID of the post creator |
| track | map | Yes | Spotify track information |
| caption | string | Yes | Optional caption, empty if unused |
| mood | string or null | Yes | Optional mood |
| createdAt | Timestamp | Yes | Post creation timestamp |
| updatedAt | Timestamp | Yes | Last post update timestamp |

#### Spotify Track Fields

| Field | Type | Description |
|---|---|---|
| spotifyId | string | Spotify track identifier |
| title | string | Track title |
| artistNames | string[] | Artist names |
| albumName | string | Album name |
| albumArtURL | string or null | Album artwork URL |
| spotifyURL | string | Link to the track on Spotify |

Example:

```json
{
  "id": "post_123",
  "authorId": "user_123",
  "track": {
    "spotifyId": "spotify_track_id",
    "title": "Example Song",
    "artistNames": ["Example Artist"],
    "albumName": "Example Album",
    "albumArtURL": null,
    "spotifyURL": "https://open.spotify.com/track/example"
  },
  "caption": "My song of the day!",
  "mood": "happy",
  "createdAt": "<Firestore Timestamp>",
  "updatedAt": "<Firestore Timestamp>"
}
```

**Notes:**
- Post IDs will be automatically generated by Firestore.
- Track metadata will be saved within each post so the app does not need to request Spotify metadata every time a post is displayed.
- Posts are readable by authenticated users.
- Only the original author can edit or delete a post.
- Initially, only captions and moods can be edited after publication.
- Post timestamps should use Firestore server timestamps.

### 3.3 Following Subcollection

**Path:** `users/{userId}/following/{followedUserId}`

Stores the users followed by a particular account.

| Field | Type | Description |
|---|---|---|
| followedUserId | string | UID of the followed user |
| createdAt | Timestamp | Time the relationship was created |

Example:

```json
{
  "followedUserId": "user_456",
  "createdAt": "<Firestore Timestamp>"
}
```

**Notes:**
- The document ID is the followed user's UID.
- A user cannot follow themselves.
- A user cannot create or remove another user's following relationships.
- Using the followed user's UID as the document ID prevents duplicate relationships.
- The initial design does not maintain a duplicate followers subcollection.

### 3.4 Likes Subcollection

**Path:** `posts/{postId}/likes/{userId}`

Stores likes associated with individual music posts.

| Field | Type | Description |
|---|---|---|
| createdAt | Timestamp | Time the post was liked |

Example:

```json
{
  "createdAt": "<Firestore Timestamp>"
}
```

**Notes:**
- The document ID is the liking user's UID.
- Each user can like a particular post only once.
- Users can create or remove only their own likes.
- Like counts may initially be retrieved through Firestore aggregation queries.
- Client-editable like count fields will not be used initially.

### 3.5 Saved Songs Subcollection

**Path:** `users/{userId}/savedSongs/{spotifyTrackId}`

Stores songs that users save to their personal collections.

| Field | Type | Description |
|---|---|---|
| track | map | Spotify track information |
| savedAt | Timestamp | Time the song was saved |

Example:

```json
{
  "track": {
    "spotifyId": "spotify_track_id",
    "title": "Example Song",
    "artistNames": ["Example Artist"],
    "albumName": "Example Album",
    "albumArtURL": null,
    "spotifyURL": "https://open.spotify.com/track/example"
  },
  "savedAt": "<Firestore Timestamp>"
}
```

**Notes:**
- The document ID is the Spotify track ID.
- Each user can save a particular song only once.
- Saved songs are private to the account owner.
- Users can add or remove only their own saved songs.

## 4. TypeScript Interfaces

Shared TypeScript interfaces will be defined in `src/types/models.ts`.

The initial interfaces are:

- `User`
- `SpotifyTrack`
- `MusicPost`
- `Follow`
- `Like`
- `SavedSong`

These interfaces will be used throughout the application to maintain consistent data structures across screens, components, and Firebase services.

Firestore document IDs must match the corresponding `uid` or `id` fields when those fields are stored within documents.

## 5. Required Firestore Queries

### 5.1 User Profiles

**Retrieve a user profile**

Read:

`users/{userId}`

**Retrieve posts created by a user**

Query the `posts` collection:
- Filter: `authorId == userId`
- Order by: `createdAt` descending
- Limit: 10 posts initially

**Retrieve users followed by an account**

Read:

`users/{userId}/following`

**Check whether the current user follows another account**

Read:

`users/{currentUserId}/following/{targetUserId}`

### 5.2 Social Feed

The social feed will display recent posts created by accounts followed by the current user.

Initial approach:

1. Retrieve the current user's following relationships.
2. Extract the followed user IDs.
3. Query posts using `authorId` filters.
4. Sort the results by creation time, newest first.
5. Display posts in the feed.

Firestore supports `in` queries with up to 30 comparison values. For larger following lists, multiple queries and result merging may be required.

Feed results should be paginated rather than loading all posts at once.

The application may later introduce a precomputed feed if query complexity or read usage becomes excessive.

### 5.3 Likes

**Check whether the current user liked a post**

Read:

`posts/{postId}/likes/{currentUserId}`

**Like a post**

Create:

`posts/{postId}/likes/{currentUserId}`

**Unlike a post**

Delete:

`posts/{postId}/likes/{currentUserId}`

**Retrieve like count**

Use a Firestore count aggregation query on the post's `likes` subcollection.

### 5.4 Saved Songs

**Retrieve saved songs**

Query:

`users/{currentUserId}/savedSongs`

Order by `savedAt` descending.

**Save a song**

Create:

`users/{currentUserId}/savedSongs/{spotifyTrackId}`

**Remove a saved song**

Delete the corresponding saved-song document.

### 5.5 Followers

The initial design stores only following relationships.

A follower list may later be implemented using a collection-group query or a trusted-backend-maintained reverse relationship.

Collection-group queries require compatible security rules and may require additional indexes.

Follower-list querying is therefore deferred until the implementation approach is finalized.

## 6. Firestore Security Rules

Security rules will be maintained in the repository's `firestore.rules` file.

### Authentication

- Unauthenticated users cannot access application data.
- Firebase Authentication determines the current user's identity.
- Users cannot impersonate another user by supplying a different UID.

### User Profiles

- Authenticated users can read public-facing profiles.
- Users can create and update only their own profiles.
- Users cannot modify their profile UID or creation timestamp.
- Profile deletion will require a separate account deletion workflow.

### Music Posts

- Authenticated users can read music posts.
- Only authenticated users can create posts.
- The post's author ID must match the authenticated user.
- Only the original author can edit or delete a post.
- The author ID and creation timestamp cannot be changed after creation.

### Following

- Authenticated users can read following relationships.
- Users can create or delete only their own following relationships.
- Users cannot follow themselves.
- Following documents cannot be edited after creation.

### Likes

- Authenticated users can read likes.
- Users can create or remove likes only under their own UID.
- Users cannot like on behalf of another account.

### Saved Songs

- Users can read only their own saved songs.
- Users can save or remove songs only in their own account.
- Saved-song documents cannot be edited after creation.

### Default Access

All database paths not explicitly covered by security rules will be denied.

The rules must be tested with the Firebase Emulator before deployment.

## 7. Required Indexes

The initial application may require the following composite indexes:

| Collection | Fields | Purpose |
|---|---|---|
| posts | authorId ASC, createdAt DESC | Retrieve a user's posts |
| posts | authorId ASC, createdAt DESC | Retrieve followed users' recent posts |

Firestore automatically creates many single-field indexes.

Additional composite indexes will be created when Firestore identifies a missing index during query development.

Indexes should be documented and committed to the repository when finalized.

## 8. Privacy Considerations

- Passwords are never stored in Firestore.
- Spotify client secrets and access tokens must not be stored in public user documents.
- Firebase configuration values do not replace security rules.
- Public profile documents should not contain private email addresses or sensitive personal information.
- Saved songs are accessible only to their owners.
- Posts and profiles are visible to authenticated users under the initial MVP model.
- Private profiles, blocking, reporting, and content moderation are future considerations.
- Account deletion must eventually remove associated user data and relationships.
